# SmartFarmOS 공개자료 조사 종합과 의사결정

- 기준일: 2026-08-12
- 목적: 공개된 상용 제품, 재배·제어 연구, 표준, 오픈소스, 국내 정책·데이터를
  현재 SmartFarmOS의 대회 범위와 대회 후 파일럿 순서로 변환한다.
- 증거 범위: 공개 문서만 사용했다. 비공개 알고리즘·프로토콜·가격·SLA·현장
  성능은 추정하거나 복제하지 않는다.
- 현재 제품 경계: 실장비가 아닌 결정적 시뮬레이터, HTTP Edge, 중앙 API,
  SQLite, 설치형 PWA로 검증한 대회용 MVP다.

## Executive Summary

1. **`insane-research`를 Codex용으로 이식할 필요는 없다.** 이번 목적은 연구
   프레임워크 자체를 만드는 것이 아니라 SmartFarmOS 의사결정에 쓸 근거를
   빠르게 확보하는 것이다. Codex의 병렬 조사, 공식 문서 우선 검색, 저장소
   대조, 독립 검증으로 필요한 효과를 더 적은 유지비로 얻을 수 있다.
2. **SmartFarmOS의 현재 차별점은 “파일럿 온실을 위한 감사 가능한 명령
   증거 계층”이다.** 구역 비교 화면만이 아니라 exact scope·만료·멱등성,
   execution journal, terminal ACK outbox, 불명확 실행 no-replay, software
   stop과 감사 이력을 한 수직 경로로 검증했다. “오픈소스”는 현재 라이선스와
   권리 확인이 BLOCK이므로 **오픈소스 공개를 목표로 한다**고만 표현한다.
3. **2026-08-27 대회 전에는 런타임 기능을 더 늘리지 않는 것이 최선이다.**
   현재 기능·회귀 게이트는 통과했지만 실제 사용자 3–5명, 자격증명 회전,
   출처·권리, 프로젝트 라이선스, 최종 보고서, 3분 이내 영상, 깨끗한 Git
   재현성이 막혀 있다. MQTT, 텔레메트리 버퍼, lease/fencing, 표준 장치
   드라이버, AI 제어를 지금 추가하면 가장 중요한 제출 증거를 약화시킨다.
4. **대회 후에는 기능명이 아니라 안전 게이트 순서로 확장한다.** 생산 신원과
   권한 → 물리 안전·수동 우선권 → 실장비 상태 재조정 → 오프라인 데이터와
   단일 Edge 소유권 → 국내 표준 어댑터·교환 프로파일 → 데이터 품질·재배
   의사결정 지원 → 제한된 자동화 순서다.
5. **외부 표준은 코어 모델이 아니라 경계 어댑터로 수용한다.** 내부
   TypeScript 계약과 중앙 API를 기준으로 유지하고, 현장에는 KS X 3267/Modbus
   또는 MQTT 어댑터, 외부 데이터에는 SPS-X KOAT-0009-7470 또는 OGC
   SensorThings 변환기를 둔다. FIWARE·EdgeX·ThingsBoard 같은 전체 플랫폼을
   코어에 편입하지 않는다.

## 1. 조사 질문과 판정 기준

이번 조사는 “회사들이 무엇을 많이 갖고 있는가”보다 아래 질문에 답한다.

1. 상용 온실 운영 제품에서 반복되는 공개 설계 원리는 무엇인가?
2. 그 원리 중 현재 SmartFarmOS에 이미 증거가 있는 것은 무엇인가?
3. 무엇을 대회 전 서사로만 사용하고, 무엇을 대회 후 구현해야 하는가?
4. 실장비·재배 데이터·안전 증거 없이 하면 안 되는 주장은 무엇인가?
5. 국내 표준과 국제 표준을 어느 경계에 연결해야 코어가 특정 업체에
   종속되지 않는가?

판정은 `채택`, `변형`, `보류`, `거부`로 통일했다. 회사의 제품 페이지는
기능 존재와 제품 방향을 확인하는 자료이지, 수율·에너지·노동 절감 효과를
독립적으로 증명하는 자료로 취급하지 않았다.

## 2. 확인된 현재 상태와 그 의미

| 확인된 사실 | 증거 | 의사결정 의미 |
| --- | --- | --- |
| PWA, 중앙 API, HTTP Edge, SQLite, 2개 시뮬레이터 경로가 있다. | [프로젝트 컨텍스트](../../.codex/project.md), [아키텍처](../architecture.md) | 새로운 플랫폼을 붙이기보다 현재 수직 경로를 제출 증거로 고정한다. |
| 명령 scope·만료·멱등성, 실행 journal, terminal ACK outbox, stop lane/fence가 검증돼 있다. | [결과보고서](../submission/result-report.md) | “명령 버튼”보다 감사 가능한 실행 생명주기가 현재 핵심 기술이다. |
| 실행 결과가 없는 `executing`은 자동 재실행하지 않고 상태 재조정을 요구한다. | [ADR 0011](../decisions/0011-durable-edge-ack-outbox.md) | 물리 exactly-once를 과장하지 않고 불확실성을 드러내는 것이 맞다. |
| 기능 검증은 PASS지만 사용자·권리·라이선스·영상·Git 게이트는 BLOCK이다. | [제출 체크리스트](../submission/release-checklist.md) | 남은 15일의 병목은 기능 수가 아니라 사람과 공개 준비 증거다. |
| MQTT, 텔레메트리 버퍼, active-active lease, 물리 인터록은 아직 없다. | [프로젝트 컨텍스트](../../.codex/project.md) | 경쟁사 조사로 빈칸을 확인할 수는 있지만 대회 기능으로 주장할 수 없다. |
| 현재 텔레메트리는 온도·습도·조도·수위 중심이다. | [공유 계약](../../packages/contracts/src/telemetry.ts) | CO₂·EC·pH·VPD·품질 표시는 계약 버전과 실제 센서 근거 뒤에 추가한다. |

따라서 이 조사에서 발견한 “좋은 기능”은 자동으로 대회 범위가 되지 않는다.
현재 완료 조건과 직접 연결되지 않는 발견은 모두 대회 후 후보로 취급한다.

## 3. 시장 구조: 한 종류의 제품이 아니다

[상용 제품 상세 조사](commercial-landscape.md)를 기능 목록이 아니라 책임
경계로 나누면 세 층이 보인다.

| 제품 층 | 대표 공개 사례 | 주된 책임 | SmartFarmOS 판단 |
| --- | --- | --- | --- |
| 현장 제어 시스템 | Priva, Hoogendoorn IIVO, Ridder HortiMaX, Argus | 센서·구동기, 기후·관수, 알람, 현장 지속성 | 복제하지 않는다. 향후 실장비 어댑터가 연결할 대상이다. |
| 운영 데이터·협업 | LetsGrow.com, Source Workspace, Autogrow API | 데이터 통합, 비교, 계획, 파트너 API | 구역 맥락·이력·감사 UX 원리는 채택한다. |
| 최적화·자율화 상위 계층 | Blue Radix, Source Cultivate/Autopilot, Koidra | 예측, 추천, 최적화, 제한적 자율 운전 | 충분한 데이터·안전·override 뒤의 선택 모듈로 보류한다. |

이 구분이 중요한 이유는 “스마트팜 OS”라는 이름이 모든 층을 직접 구현해야
한다는 뜻이 아니기 때문이다. SmartFarmOS는 현재 두 번째 층의 운영·감사
경험과 첫 번째 층을 향한 안전한 Edge 경계를 증명한다. 향후에도 현장 제어기와
분석 모듈을 교체할 수 있는 계약을 유지하는 편이 현실적이다.

### 상용 제품에서 반복되는 공개 원리

1. **장치보다 작물·구역·재배 맥락이 먼저다.** 데이터가 어느 구역과 작기에
   속하는지 알아야 비교와 의사결정이 가능하다.
2. **기후·관수·에너지·알람은 같은 운영 문맥에서 읽혀야 한다.** 다만 한 화면에
   모은다는 것과 한 제어 알고리즘에 결합한다는 것은 다르다.
3. **자율화보다 데이터 정합성, override, alarm, audit가 먼저다.** 공개된
   자율화 제품도 기존 제어기와 운영자 경계를 전제로 한다.
4. **API와 파트너 생태계가 제품 범위를 확장한다.** 내부 코어에 모든 기능을
   넣기보다 계약으로 연결한다.
5. **설치·온보딩·지원이 기능만큼 중요하다.** SmartFarmOS도 장치 오류·시간
   불일치·자격증명·복구 절차를 사용자에게 설명할 수 있어야 한다.

여기서 얻는 결론은 “경쟁사와 같은 기능을 더 만들자”가 아니라 “현재
SmartFarmOS의 책임과 비책임을 더 선명하게 하자”이다.

### 대회에서 기억시킬 한 문장과 주 사용자

> SmartFarmOS는 중소형 시설원예 운영자가 구역별 이상을 확인하고, 검토한
> 관수 요청이 장치의 최종 결과와 감사 기록으로 남았는지 추적하는
> **파일럿용 명령 증거 계층**이다.

대회 발표의 주 사용자는 `중소형 온실 운영자` 한 명으로 고정한다. 통합업체,
대학·연구 온실, 공공 실증단지는 대회 후 도입 후보이지 같은 장표의 주 고객으로
나열하지 않는다. 일반 IoT dashboard와의 차이는 그래프 개수가 아니라 명령의
scope·만료·중복 방지·terminal ACK·재시작 복구·수동 정지 인과관계를 하나의
증거로 보존하는 데 있다.

### 운영자 업무로 다시 본 제품

[운영자 워크플로 조사](operator-workflows-maintenance.md)에서 반복된 실제 루프는
`commissioning -> 작기/구역 -> 일일 모니터링 -> 알람 분류·확인 -> 수동 우선
제어 -> 관수 근거 -> 센서 교정·정비 -> 정전/통신 복구 -> 인수인계·지원`이다.
SmartFarmOS는 이 중 작기/구역, 알람 ack, ACK 기반 결과, software stop, 최근
수위 근거까지 시연할 수 있다. 교정·정비 로그, 알람 escalation, 운영자 복구
안내, 인수인계는 아직 없다.

따라서 대회 전 사용성 세션에는 새 기능 대신 아래 질문을 추가한다.

- 센서값이 이상할 때 화면 밖에서 무엇을 먼저 확인하는가?
- 정전·통신 복구 뒤 반드시 보여야 할 상태와 문구는 무엇인가?
- `확인`, `승인`, `적용`, `완료`, `정지`를 서로 다르게 이해하는가?
- 다음 교대자에게 대상·원인·조치·결과 중 무엇을 남겨야 하는가?

이 답은 대회 후 commissioning, calibration/maintenance, outage runbook,
handover UX의 순서를 정하는 실제 사용자 근거가 된다.

## 4. 재배·제어 로직을 도입하는 안전한 사다리

재배 제어는 센서값에서 곧바로 구동 명령으로 건너뛰면 안 된다. 기능은 아래
순서로 승격하고 각 단계의 증거가 없으면 다음 단계로 넘어가지 않는다.

| 단계 | 제품 동작 | 필요한 증거 | 현재 판정 |
| --- | --- | --- | --- |
| 0. 관측 | 원시값, 단위, 시간, 구역을 보존 | 계약 검증, 시간·순서·범위 검사 | 현재 범위 유지 |
| 1. 품질 | stale/offline/suspect/calibration 상태 표시 | 실제 센서 특성, 결측·드리프트 시험 | 대회 후 P0 |
| 2. 파생 지표 | VPD 등 계산값과 입력·식을 함께 표시 | 식·단위·유효 범위, 불확실성 표시 | 대회 후 P1 |
| 3. 설명·추천 | 목표선 편차, 가능한 원인, 운영자 확인 | 작물·생육단계별 근거와 오경보 평가 | 대회 후 P1 |
| 4. 승인형 실행 | 사용자가 범위·기간·제약을 확인하고 실행 | 현재 명령·ACK·감사 + 실장비 안전 | 실장비 뒤 확장 |
| 5. 제한 자동화 | deadband/rule/PID 등 명시적 제한 안에서 실행 | fail-safe, override, 상태 재조정, 현장 시험 | 대회 후 P2 |
| 6. 최적화·MPC | 예측 모델이 비용·생육·제약을 함께 최적화 | 장기 데이터, 모델 검증, drift 감시, rollback | 연구·파일럿 |

온도·상대습도로 계산한 공기 VPD도 잎 온도와 작물 상태를 모르면 실제 증산
부담을 완전히 설명하지 못한다. 같은 이유로 토양·배지 수분, 일사, CO₂, EC,
pH를 확보하지 않은 상태에서 “최적 관수”나 “수확량 최적화”를 주장하지 않는다.
파생 지표는 원시 입력, 계산 버전, 품질 상태를 함께 보존해야 한다.

## 5. 표준과 오픈소스의 자리

[국제 표준·Edge·보안 조사](open-standards-edge-security.md)와
[국내 표준·공공데이터 조사](korea-standards-and-data.md)를 현재 구조에 대입하면
아래처럼 작은 경계가 적합하다.

```text
현장 장치/기존 제어기
  -> Edge transport adapter (향후 KS X 3267/Modbus, MQTT, 필요 시 OPC UA)
  -> SmartFarmOS versioned contracts + HTTP API + audit/ACK
  -> export adapter (향후 SPS-X KOAT-0009-7470, OGC SensorThings)
  -> 외부 분석·공공데이터·파트너 서비스
```

| 후보 | 결정 | 이유 |
| --- | --- | --- |
| 현재 TypeScript 계약·HTTP 중앙 경계 | 채택·유지 | 이미 테스트·감사·재현 경로가 있다. |
| KS X 3267/Modbus | 대회 후 변형 | 실장비와 원문 기반 codec을 Edge 어댑터로 격리한다. |
| MQTT 5 | 대회 후 변형 | TLS·topic ACL·내구 queue와 함께 선택형 입력 어댑터로 쓴다. |
| SPS-X KOAT-0009-7470 | 대회 후 우선 검토 | 국내 데이터 교환 profile 후보이며 내부 모델을 대체하지 않는다. |
| OGC SensorThings | 대회 후 변형 | 읽기·내보내기 표준 표면 후보로 적합하다. |
| OPC UA·LoRaWAN | 장비 의존 보류 | 실제 도입 장비가 요구할 때만 어댑터를 추가한다. |
| Sparkplug B | 참고 | birth/death와 상태 관리 개념은 유용하지만 지금 전체 규약은 과하다. |
| oneM2M·FIWARE·EdgeX·ThingsBoard·Mainflux | 코어 채택 거부 | 현재 규모에서 전체 플랫폼 도입은 중복 책임과 운영 부담이 크다. |
| farmOS | 상호운용 참고 | 재배 기록·농장 관리 영역과 연결 가능하지만 제어 코어 대체재는 아니다. |

“표준을 고려했다”와 “표준 호환 제품이다”는 다르다. KS 원문 조항, 실제
레지스터, 장비, 적합성 시험이 없는 현재는 호환을 주장하지 않고 “표준
어댑터를 분리할 수 있는 구조”라고만 설명한다.

[오픈소스 구현 비교](open-source-reference-implementations.md)도 같은 결론을
보강한다. farmOS의 농장 기록 도메인, ThingsBoard Gateway·EdgeX의 connector
분리, Home Assistant·OpenAg의 local-first 원리는 참고할 가치가 있다. 그러나
ThingsBoard, MainfluxLabs/Magistrala, Orion-LD, OpenRemote 같은 전체 플랫폼을
현재 코어에 넣으면 중복 책임·운영 비용·라이선스 검토 범위가 커진다. 대회 전
새 production dependency는 추가하지 않고, 첫 실장비 transport가 확정된 뒤
필요한 adapter pattern 하나만 다시 검토한다.

## 6. 대회 전 범위 잠금

### 지금 실행할 것

1. 실제 농업 종사자 또는 도메인 대리 사용자 3–5명의 익명 과업 세션을
   완료하고, 실패·혼란·안전 중단까지 그대로 집계한다.
2. 자격증명 회전, 기존 성과의 출처·권리, 프로젝트 라이선스, AI 사용 고지를
   저장소 소유자가 실제 증거로 확정한다.
3. 현재 검증된 흐름과 비주장을 맞춘 결과보고서·발표·3분 이내 영상을
   완성한다.
4. 경쟁사·표준 조사는 “향후 확장 근거”로 인용하되 구현 완료처럼 표현하지
   않는다.
5. 현재 테스트·브라우저 흐름·의존성 선언 검사를 다시 통과시키고 최종
   소스와 제출물의 숫자를 일치시킨다.

### 지금 구현하지 않을 것

- MQTT broker·adapter, 텔레메트리 오프라인 queue, device shadow
- 다중 Edge lease/fencing, active-active 실행
- KS/Modbus/OPC UA 실제 드라이버와 호환·인증 주장
- CO₂·EC·pH·VPD 신규 계약과 대시보드
- PID·MPC·AI 추천·자율 관수·수확 예측
- 외부 SaaS, 대형 IoT 플랫폼, 새 운영 의존성
- 기존 상용 제품의 화면·문구·비공개 로직 복제

### 범위 잠금의 예외

잠금은 `새 capability 0개`라는 뜻이다. 3–5명 사용성 세션에서 발견된 P1
안전·과업 차단 문제, 현재 claim을 지키기 위한 회귀 수정, 제출·개인정보·접근성
결함은 기존 계약과 테스트 안에서 고칠 수 있다. 반대로 새 metric, transport,
driver, 외부 서비스, 자동화 단계, 표준 호환 claim이 생기면 사용성 개선이라는
이름이어도 대회 후로 보낸다.

이는 해당 기능의 가치가 낮아서가 아니다. 현재 제출의 실제 병목과 완료
조건을 기준으로 보면, 지금 추가하는 편이 검증·안전·설명 일관성을 해치기
때문이다.

## 7. 대회 후 게이트 기반 로드맵

### Gate 1 — 공개·운영 기본기

완료 조건: 권리와 라이선스가 확정되고, 비밀정보가 제거되며, 생산용 신원과
역할 경계 및 백업·복구 절차가 검증된다.

- OIDC/OAuth2 기반 사용자·조직·사이트 권한
- Edge 장치별 자격증명 발급·회전·폐기
- 운영 로그, 보존 기간, 백업·복구 리허설
- 취약점 신고·업데이트·지원 정책

### Gate 2 — 안전한 실장비 파일럿

완료 조건: 실제 장치에서 수동 우선권, 독립 비상정지/인터록, 로컬 제한,
통신 단절, 재시작, 불명확 실행의 안전 상태를 독립 확인한다.

- 물리 인터록과 소프트웨어 stop의 책임 분리
- 장치 상태 조회와 `recovery_required` 해소 절차
- 특정 장비에 필요한 KS X 3267/Modbus 등 최소 어댑터
- 명령 용량·시간·빈도 제한과 현장 점검표
- 센서 교정·드리프트·stale/suspect/offline 품질 모델

### Gate 3 — 끊김과 다중 Edge를 견디는 운영

완료 조건: 장시간 네트워크 단절과 복구, 중복·역순 데이터, Edge 교체와
동시성 시험에서 데이터와 실행 소유권이 일관된다.

- MQTT TLS·topic ACL 또는 필요한 현장 transport
- 텔레메트리 durable buffer와 재전송·중복 제거
- desired/reported 상태와 재조정 규칙
- 단일 장치 owner lease와 fencing token
- 시간 동기화·sequence·out-of-order 정책

### Gate 4 — 상호운용 데이터와 재배 지원

완료 조건: versioned fixture와 round-trip 시험으로 외부 교환이 내부 모델을
손상하지 않고, 실제 사용자에게 설명 가능한 판단 근거를 제공한다.

- SPS-X KOAT-0009-7470 교환 profile
- OGC SensorThings 읽기/export adapter
- 장기 시계열, downsampling, 데이터 품질 표시
- CO₂·EC·pH 등 실제 설치 센서의 versioned 계약
- VPD·목표선·편차 설명과 전략 버전 diff/rollback
- 알람 규칙 template, escalation, 알림 provider

### Gate 5 — 제한된 최적화

완료 조건: 기준 전략보다 안전성과 성능이 나쁘지 않음을 별도 데이터로
검증하고, 운영자가 모델 버전·입력·권고 이유를 보고 override·rollback할 수
있다.

- 먼저 advisory와 shadow evaluation
- 다음으로 승인형 실행
- 마지막에 bounded rule/PID/MPC 또는 선택형 최적화 모듈
- 모델 drift, 농장 간 일반화 실패, 센서 고장, 통신 단절을 지속 평가

있지만 4–5번보다 자율화가 먼저 올 수는 없다.

### 파일럿 가치를 측정하는 방법

[경제성·KPI 조사](economics-kpi-product-positioning.md)에 따르면 온실의 공개
비용 근거는 에너지, 물·관수, 노동, 질병·고장·환경이탈 손실로 모인다. 하지만
SmartFarmOS가 이 비용을 줄였다는 실농가 증거는 아직 없다. 따라서 대회에서
일반 ROI·절감률을 만들지 않고, 파일럿에서 먼저 아래 운영 지표를 측정한다.

| KPI 축 | 첫 측정값 | 해석 경계 |
| --- | --- | --- |
| 데이터 신뢰성 | telemetry freshness, stale duration | 센서 정확도·교정 성능과 구분 |
| 알람 대응 | ack median/p95, alarm-to-action time | 손실 회피 금액은 별도 baseline 필요 |
| 명령 결과 | terminal ACK 성공률, final-off 완료율 | 물리 exactly-once를 의미하지 않음 |
| 복구 | ACK replay 성공, `recovery_required` 건수 | telemetry offline queue는 현재 미구현 |
| 수동 안전 | stop 결과와 전파 시간 | 물리 E-stop·interlock과 구분 |
| 관수 운영 | 저수위 재발, missed/duplicate event | `L/kg`는 실제 유량·수확 데이터 뒤 계산 |

실제 파일럿 뒤에만 `kWh/m2/day`, `L/kg`, `labor-minutes/alarm`, `kg/m2/cycle`,
회피 손실과 설치·교육·운영 비용을 함께 비교한다. 공개 가격이 없는 경쟁사의
ROI를 대신 추정하지 않는다.

## 9. 시뮬레이터와 향후 평가 시나리오

현재 시뮬레이터는 제품 주장을 넓히는 도구가 아니라 실패를 반복 가능하게
만드는 도구로 유지한다. 향후 기능은 최소한 아래 범주로 평가한다.

| 범주 | 주입할 상황 | 기대하는 불변조건 |
| --- | --- | --- |
| 센서 품질 | 결측, stuck-at, drift, spike, 단위 오류, 미래 시간 | 품질 상태를 표시하고 안전 판단에서 제외한다. |
| 네트워크 | 단절, 느린 복구, 중복, 역순, 부분 업로드 | 원본을 잃지 않고 중복 결과를 만들지 않는다. |
| Edge 수명주기 | 명령 전·중·후 crash, DB 손상, 오래된 프로세스 복귀 | 불명확 실행을 재실행하지 않고 stale owner를 차단한다. |
| 구동기 | 무응답, 지연, 반대 상태, 로컬 제한 작동 | 성공 ACK를 만들지 않고 수동 안전 절차로 전환한다. |
| 재배 규칙 | 경계값 진동, 급격한 외기 변화, 센서 간 불일치 | hysteresis·deadband·최소 on/off와 설명을 보존한다. |
| 모델 | 계절 변화, 품종 변화, 입력 누락, 분포 이동 | advisory를 낮추거나 중단하고 기준 전략으로 rollback한다. |

시뮬레이터 통과는 실제 장치 안전, KS 적합성, 재배 성과를 증명하지 않는다.
실장비 파일럿에서는 hardware-in-the-loop와 독립 수동 점검표가 별도로 필요하다.

## 10. 제품 문구와 지식재산 경계

### 현재 말할 수 있는 것

- “결정적 시뮬레이터에서 구역 비교부터 명령·ACK·감사까지 재현했다.”
- “Edge가 terminal ACK를 내구 저장하고, 결과가 불명확하면 자동 재실행하지
  않는 경계를 검증했다.”
- “국내외 표준을 코어에 고정하지 않고 Edge·export 어댑터로 연결할 계획이다.”
- “상용 온실 제어기를 대체하는 것이 아니라 운영·감사 경계부터 오픈소스로
  공개할 수 있도록 검증한다. 현재는 권리·라이선스 확정 전이다.”

### 현재 말하면 안 되는 것

- “Priva·IIVO·HortiMaX와 동등한 기후 제어기다.”
- “KS 호환·인증 제품이다.”
- “실농가에서 수율·에너지·노동을 개선했다.”
- “네트워크 단절 중 telemetry와 장치 제어가 완전 보장된다.”
- “물리 exactly-once, 비상정지, 인터록을 제공한다.”
- “AI가 최적 관수·기후를 자율 제어한다.”

공개 제품에서 가져올 것은 문제 분해, 안전 경계, 데이터 계약 같은 일반
원리다. 화면 배치, 문구, 이미지, 비공개 API, 역공학한 프로토콜, 제어 파라미터
또는 알고리즘을 복제하지 않는다.

## 11. 남은 사실 확인과 의사결정

1. 실제 첫 파일럿의 작물, 시설 유형, 제어기·센서 모델은 무엇인가?
2. 파일럿 장비가 요구하는 전송 규격과 합법적으로 이용 가능한 레지스터
   문서는 무엇인가?
3. 사용자가 가장 먼저 비용을 지불할 문제는 알람·복구, 관수 증거, 재배
   비교, 규정·보고 중 무엇인가?
4. 센서 데이터의 소유권, 보존, 외부 분석 제공 동의는 어떻게 분리할 것인가?
5. 프로젝트 라이선스와 기존 교육 성과 재사용 권리가 어떤 플러그인·데이터
   공개 범위를 허용하는가?
6. 실장비 안전 시험과 국내 적합성 시험을 수행할 기관·예산·책임자는 누구인가?

이 질문에 답하기 전에는 특정 장비 통합, 데이터 플랫폼, 예측 모델을 선택하지
않는다.

### 현재 권고를 뒤집는 증거

아래 중 하나가 실제로 확인되면 “범위 잠금 + 명령 증거 계층” 전략을 다시
검토한다.

1. 3–5명 사용성 세션에서 핵심 과업이 반복 실패하고 claim-preserving 수정으로
   해결되지 않는다.
2. 기존 성과의 권리 또는 OSI 라이선스 선택이 불가능해 공개 소프트웨어
   포지션 자체를 사용할 수 없다.
3. 공식 대회 규칙이 실장비 증거나 특정 상호운용 기능을 필수로 요구한다.
4. 첫 파일럿 사용자가 MQTT/Modbus 연결 없이는 명령 증거 계층의 가치를 전혀
   평가할 수 없다고 확인한다.
5. 실제 사용자들이 알람·ACK·감사보다 예측·생산 계획을 일관되게 더 높은
   지불 문제로 평가한다.
6. 현재 검증이 깨져 남은 기간에 복구할 수 없고 기능 범위를 더 줄여야 한다.
