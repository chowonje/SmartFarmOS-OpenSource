# Slice E 농업 종사자 현장 사용성 검증

## 상태와 완료 조건

이 문서는 SmartFarmOS 대회용 로컬 데모의 진행자용 프로토콜이다. 실제
농업 종사자 또는 역할이 명시된 도메인 대리 사용자 3~5명의 세션 기록이
채워지기 전에는 Slice E를 완료로 표시하지 않는다. 자동화된 브라우저
테스트와 AI 검토는 세션 준비 증거일 뿐 실제 사용자 검증을 대체하지 않는다.

검증 대상은 simulator-backed contest MVP다. 실제 펌프, MQTT 장치, 생산
계정 또는 농장 데이터는 사용하지 않는다.

## 검증할 결정

이 검증은 운영자가 별도 교육 없이 다음 흐름을 이해하고 안전하게 수행할
수 있는지 판단한다.

```text
주의 구역 발견 → 원인/시점 설명 → 알람 확인 → 올바른 구역에 전략 적용
→ 장치 결과와 처리 주체/시각 확인
```

## 참가자와 표본

- 총 3~5명
- 가능하면 현직 또는 최근 2년 내 시설원예·스마트팜 운영 경험자 2명 이상
- 대체 참가자는 농업 지도사, 관련 전공자, 온실 운영 보조자처럼 역할과
  한계를 설명할 수 있는 도메인 대리 사용자만 포함
- 구현에 직접 참여한 개발자는 본 표본에 포함하지 않음
- 4명 이상이면 데스크톱과 모바일을 각각 2세션 이상 포함
- 이름, 연락처, 농장명은 기록하지 않고 `S01`~`S05` 코드만 사용

## 핵심 지표와 판정 기준

### 1. 무도움 과업 완료

각 참가자가 다섯 과업을 진행자의 위치·버튼 지시 없이 완료했는지 기록한다.
5명 기준 각 과업에서 4명 이상 완료가 임시 통과선이다. 3명만 확보한 경우
안전 관련 과업 4·5는 3명 모두 완료해야 하며, 표본 부족을 결과에 명시한다.

### 2. 올바른 운영 판단

다음 네 항목을 모두 맞혀야 한 세션의 판단이 정확한 것으로 센다.

- 주의 구역: 2번 베드
- 원인 지표: 수위
- 적용 대상: 2번 베드만 선택
- 결과 근거: ACK 기반 완료 상태와 감사 기록

### 3. 결과 도달 시간

세션 시작부터 과업 5 완료까지의 시간과 과업별 시간을 기록한다. 첫 3~5명은
기준선 수집이므로 시간 자체를 합격선으로 사용하지 않는다. 중앙값과 가장
오래 걸린 단계가 다음 UI 수정 우선순위를 정한다.

### 진단 지표

- 도움 요청 횟수와 도움을 요청한 문장
- 잘못 선택했다가 수정한 구역·버튼 수
- 뒤로 가기 또는 다른 메뉴 왕복 횟수
- 이해하지 못한 용어와 참가자의 원문 표현
- 완료 후 신뢰도 1~5점

### 안전 가드레일

- 잘못된 구역에 실제 적용 요청 제출: 허용 0건
- pending 상태에서 중복 적용 요청 제출: 허용 0건
- “5초 장치 로컬 종료는 물리 인터록·실장비 안전을 증명하지 않는다”는
  의미를 디브리핑 전에 정확히 설명:
  5명 중 4명 이상, 또는 3명 표본이면 전원
- 실제 장치 또는 생산 자격증명 사용: 허용 0건

가드레일 위반, 데이터 손실, 다른 농장 범위 노출, 잘못된 완료 표시가 한 번이라도
발생하면 제출 리허설을 중단하고 P1로 수정·재검증한다.

현재 화면은 각 대상의 최근 수위·저수위 알람 근거를 보여주고, 선택한
구역, 5초 시간제 실행, 물리 인터록 미검증을 명시적으로 확인해야만
기본 V2 전략을 적용할 수 있다. 최근
저수위 알람 대상이 아닌 구역은 예외 경고를 보여준다. 확인은 대상/전략을
바꾸거나 한 번 제출하면 초기화된다. 이는 우발적 제어를 줄이는 화면 가드일이며,
시스템이 농업적 정답 구역을 자동 승인한다는 의미는 아니다. 따라서 실제 참가자의
오구역 제출 0건 가드레일은 그대로 측정한다.

## 세션 준비

1. 저장소 루트에서 최신 검증을 실행한다.

   ```bash
   npm run verify
   ```

2. 세션마다 새 익명 코드와 별도 SQLite 파일을 사용한다. `artifacts/`와
   `*.sqlite`는 Git에서 제외된다.

   ```bash
   npm run demo:usability -- S01
   ```

3. `http://127.0.0.1:4173`을 열고 온라인 상태, 두 구역, 네 지표, 활성
   저수위 알람을 확인한다. 관수 화면에서 2번 베드의 저수위
   근거, 오구역 예외 경고, 5초 장치 로컬 종료 경계, 적용 전 확인,
   완료 후 재확인 잠금과 제어 화면의 `즉시 정지 (소프트웨어)` 안내도
   사전 리허설한다. 세션 실행기는 5초 지표 갱신을 유지하면서 저수위
   회복 시점을 기본 120회 배출 후로 늦춰 첫 과업 중 알람이 사라지지
   않게 한다.
4. 참가자에게 메뉴 위치나 정답 구역을 보여주지 않는다.
5. 모바일 세션은 참가자가 평소 사용하는 브라우저 또는 390×844 수준의
   실제/에뮬레이션 화면에서 진행한다.
6. 녹화는 별도 동의가 있을 때만 한다. 기본 증거는 익명 관찰표와 비식별
   화면 캡처다.

세션 파일을 재사용하면 이전 알람 확인과 명령 이력이 남아 과업이 달라진다.
항상 새 코드를 사용한다. 중단된 동일 세션만
`npm run demo:usability -- S01 --resume`으로 이어서 실행한다. 실행 명령은
기존 세션 파일을 자동 삭제하지 않는다.

## 진행자 대본

시작할 때 다음 내용만 읽는다.

> 이 화면은 실제 장치가 아닌 대회용 시뮬레이터입니다. 평소 농장을
> 확인하듯 자유롭게 살펴보세요. 제가 버튼 위치는 알려드리지 않지만,
> 생각하는 내용을 말로 설명해 주세요. 막히면 도움을 요청할 수 있고 그
> 지점 자체가 중요한 결과입니다.

참가자에게 한 번에 하나씩 다음 과업만 제시한다.

1. 현재 가장 주의가 필요한 구역을 찾으세요.
2. 어떤 지표가 언제부터 기준을 벗어났는지 설명하세요.
3. 해당 알람을 확인 처리하세요.
4. 검토된 관수 프리셋을 올바른 구역에 적용하세요.
5. 실제 명령 결과와 누가 언제 처리했는지 확인하세요.

진행자는 침묵을 깨기 위한 “지금 무엇을 찾고 계신가요?”만 사용할 수 있다.
메뉴명, 정답 구역, 버튼명 또는 다음 행동을 말하면 그 과업은 `도움 필요`로
기록한다.

## 안전 이해 확인과 디브리핑

과업 4 직후, 안내를 추가하기 전에 질문한다.

> 지금 보낸 관수 요청은 언제 어떤 상태로 끝나나요? 화면의 5초 시간제
> 종료와 `즉시 정지 (소프트웨어)`를 실제 펌프의 물리 안전장치나
> 비상정지라고 볼 수 있나요? 그렇게 판단한 화면 근거는 무엇인가요?

정답은 “시뮬레이터 장치가 5초 동안 실행하고 로컬 타이머로 `off`가 된
뒤 완료되며 소프트웨어 정지는 실행 중 타이머를 중단하지만, 둘 다 물리
비상정지·인터록·실장비 검증·수분 피드백 폐루프 제어를 의미하지 않는다”이다.
오답이면 즉시 simulator-only 한계를 설명하고 실제
장치에서 이 동작을 재현하지 않도록 안내한다.

마지막에 다음을 묻는다.

- 이 결과를 실제 작업 판단에 얼마나 신뢰할 수 있나요? 1~5점
- 가장 불안하거나 이해하기 어려웠던 지점은 무엇인가요?
- 평소 사용하는 표현으로 바꾸고 싶은 용어는 무엇인가요?

## 판정과 후속 조치

- `통과`: 모든 안전 가드레일 충족, 과업별 임시 통과선 충족, P1 없음
- `조건부`: 가드레일은 충족했지만 한 과업이 통과선 미달이거나 반복되는 P2가 있음
- `실패`: 가드레일 위반, P1, 또는 핵심 흐름을 다수 참가자가 완료하지 못함

P1은 수정 후 영향을 받은 과업을 최소 2명의 새 참가자 또는 원 실패 참가자의
재검증으로 다시 확인한다. P2는 같은 지점이 2명 이상에게 반복되면 대회 제출
전에 수정한다. 개별 취향이나 문구 제안은 P3로 기록하고 안전·완료율보다 먼저
최적화하지 않는다.

각 세션은 [facilitator-quickstart.md](./facilitator-quickstart.md)와
[session-template.md](./session-template.md)를 따라 기록한다.
세션 종료 후 참가자별 결과를 합산하되, 작은 표본을 일반 농업 종사자 전체의
통계로 표현하지 않는다.

Markdown 관찰표는 로컬 원본으로 보존하고, 제출·집계용 비식별 결과는
관찰표를 보며 대화형 기록기로 만든다. 기록기는 기존 결과를 덮어쓰지 않고
완전한 strict schema만 저장한다.

```bash
npm run usability:record -- S01
```

[session-result.example.json](./session-result.example.json)은 wire 예시와 수동
복구용이다. 결과 JSON은 이름·연락처·원문 메모 필드를 허용하지 않는다.
3–5개 결과가 준비되면 다음을 실행한다.

```bash
npm run usability:summarize
```

집계기는 비식별 필드, 세션 코드·파일명 일치, 중복 코드, 오구역·pending
중복 제출, 실장비/생산 자격증명 사용, 안전 이해 기준, 미해결 P1을 거부한다.
이슈의 `pattern`은 `command-result-location`과 같은 공통·비식별 slug로 기록하며,
같은 미해결 P2 pattern이 서로 다른 2개 이상 세션에서 반복되면 제출 게이트를
실패한다. 재검증 `passed`는 전체 이슈 수는 보존하되 미해결 반복 집계에서는
제외한다. 결과는 `artifacts/usability/summary/` 아래에만 쓴다.
