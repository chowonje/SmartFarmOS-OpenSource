# SmartFarmOS Contract V1

The central HTTP mapping and status-code policy are defined in `docs/contracts/http-v1.md`.

## Consumers

| Consumer | Writes | Reads |
| --- | --- | --- |
| Device simulator or physical device adapter | `Telemetry`, `CommandAck` | `Command` |
| Edge Gateway | validated `Telemetry`, `CommandAck` | raw device input, validated `Command` |
| Central API | `Command`, catalog/crop-cycle state, alarm state, irrigation strategy/application state, audit events, and command lifecycle state | `Telemetry`, `CommandAck` |
| User PWA | crop/cycle mutations, alarm acknowledgement, strategy application, and user command intent | validated farms, devices, growing areas, crop cycles, approved strategies, application results, alarms, audit events, crops, telemetry, individual command projections, and bounded command history |
| PWA/API platform hosts | reviewed module implementations | strict `ModuleManifestV1` metadata and registry configuration |

## Versioned Objects

Every object is a strict JSON object with a literal `schemaVersion`. Unknown fields fail validation so accidental credential or implementation fields cannot silently cross a boundary.

The open-platform composition contract is documented separately in
`docs/contracts/module-manifest-v1.md`. It is a build-time/runtime-startup
contract and does not change the existing HTTP V1 payloads.

### Farm

- Identifier: `farm:<slug>`
- Required: `name`, IANA-style `timezone`, `createdAt`

### Device

- Identifier: `device:<slug>`, scoped together with its `farmId` rather than
  globally unique across all farms
- Required farm scope and declared capabilities
- Status: `online`, `offline`, or `degraded`

### GrowingArea

- Identifier: `area:<slug>`, scoped together with its `farmId` rather than
  globally unique across all farms
- Required name, `kind`, status, creation time, and update time
- Kind: `greenhouse`, `bed`, or `tank`
- Status: `active` or `inactive`
- `primaryDeviceId` is a nullable comparison/control representative and, when
  present, must reference a registered device in the same farm

### CropCycle / CropCycleDetail

- Identifier: `cycle:<slug>`, scoped together with its `farmId` rather than
  globally unique across all farms
- Required name, crop name, status, creation time, and update time
- Optional variety, start time, and planned end time are normalized to strings
  or `null`; when both dates exist, the planned end must be later than the start
- Status: `planned`, `active`, or `completed`
- `CropCycleDetail` keeps the cycle record separate from its non-empty, unique
  `areaIds` assignment list
- Every assigned area must belong to the same farm, and one area cannot belong
  to two active crop cycles at the same time
- The API owns IDs, farm scope, and timestamps; create/patch requests cannot
  overwrite them

### CropRecord

- Identifier: `crop:<slug>`
- Required farm scope, name, health status, creation time, and update time
- Optional association to a registered device in the same farm
- Health status: `good`, `fair`, or `poor`
- Optional manager and notes are normalized to strings or `null`
- The API owns IDs and timestamps; create/patch requests cannot overwrite them

### Telemetry

- Identifier: `telemetry:<slug>`
- Required farm/device scope, non-negative sequence, observation time, metric, value, and unit
- Allowed pairs: temperature/celsius, humidity/percent, illuminance/lux, water level/percent
- Values outside the metric safety range fail validation

### AlarmRule

- Identifier: `alarm-rule:<slug>`, stored with required farm/cycle/area/device scope
- Required name, metric, `above` or `below` comparison, bounded threshold,
  `warning` or `critical` severity, enabled state, and timestamps
- The area must use the target device as its representative and be assigned to
  the target crop cycle

### AlarmInstance

- Identifier: deterministic `alarm:<slug>` generated from the farm, rule, and
  first breached telemetry ID
- Required rule/cycle/area/device snapshot, severity, trigger/latest telemetry
  IDs, observed value and timestamps
- Condition state is `active` or `cleared`; only cleared instances carry
  `clearedAt`
- A nullable acknowledgement stores actor ID and time independently from the
  condition state, so a later clear retains the operator evidence

### AuditEvent

- Identifier: deterministic `audit:<slug>`
- V1 retains required farm/cycle scope, typed actor, action, target,
  success/failure result, occurrence time, and at most 20 bounded scalar detail
  entries
- V2 is additive and limited to a direct `command.completed` target with
  `cycleId: null`; typed details require `source: direct`, device, requested
  action, terminal outcome, and any manual-stop cause
- Implemented actions: `alarm.acknowledged`, `command.completed`, and
  `strategy.applied`
- Events are inserted append-only; exact acknowledgement/application ACK replays
  do not create another row
- Existing/default list queries exclude unscoped V2 rows. A reviewed client
  requests `includeUnscoped=true` to combine farm-level direct control with an
  optional selected-cycle trail.

### IrrigationStrategy

- Identifier: `strategy:<slug>` with immutable version `1..9999`
- Required farm/cycle scope, name, optional description, pump state, status, and
  timestamps
- Optional `runDurationSeconds` is bounded to `1..300`, is allowed only for an
  `on` strategy, and selects the device-local timed V2 command path
- Status: `draft`, `approved`, or `retired`; an approved strategy requires
  `approvedAt`, while a draft cannot carry one
- The current contest demo lists and applies approved strategies only

### StrategyApplication / StrategyApplicationTarget

- Identifier: `strategy-application:<slug>`
- Snapshots farm/cycle scope, strategy ID/version/name, pump state, optional
  run duration, actor,
  idempotency key, and one to 20 unique area/device/command targets
- Target state reuses the command lifecycle and carries either a resulting pump
  state or a failure reason according to its terminal status
- Aggregate state is `pending`, `succeeded`, `partial`, or `failed` and must
  agree with all target states
- Records without a run duration retain the V1 immediate state behavior;
  records with a duration remain pending until the device returns final `off`
- The contract does not claim sensor-feedback, a physical interlock, or
  real-hardware timing proof

### Command

- Identifier: `command:<slug>`
- Required farm/device scope, actor, idempotency key, issue time, and expiry time
- V1 action: `set_pump_state` with `on` or `off`
- V2 action: `run_pump_for` with integer `durationSeconds: 1..300`; its requested
  state is `on` and its successful terminal state is `off`
- Expiry must be later than issue time and no more than five minutes later
- Reusing a command ID or idempotency key with different content is rejected as an idempotency conflict
- `CommandProjection` combines the immutable command with `pending`,
  `acknowledged`, `failed`, or `timed_out` lifecycle state, its optional terminal
  acknowledgement, and `updatedAt`
- `CommandListResponse` returns at most 100 projections; the HTTP query defaults
  to 50 and can optionally restrict the result to one registered same-farm
  device

### CommandAck

- Must repeat command, farm, and device identity
- Status: `acknowledged`, `rejected`, `failed`, or `timed_out`
- ACK V1 retains the original success/failure shape and reason codes.
- Acknowledged results carry the resulting pump state and no reason code
- An acknowledged result must match the command's expected final state; V2
  timed runs therefore cannot complete with `pumpState: on`
- Non-acknowledged results carry a reason code and no success result
- Additive ACK V2 represents only a software manual-stop decision. It carries
  `reasonCode: manual_stop`, `result: null`, `status: failed | rejected`, and a
  required different `causedByCommandId` that points to the V1 pump `off`
  command. It is compatible with a V1 `on` or timed V2 activation, never with a
  V1 `off` target.
- The central store validates that the cause exists, is a same-farm/same-device
  V1 `off` with an acknowledged final-`off` result, does not predate the
  activation, and is not later than the ACK.
- The Edge persists the exact terminal ACK before central submission and may
  resend it verbatim after restart. This delivery journal is internal and adds
  no field to `CommandAck V1`; ACK V2 is an additive union member.
- A command journaled as `executing` without a terminal ACK is not automatically
  rerun; device-state reconciliation remains outside this wire contract.

## Breaking-Change Report

There was no formal legacy contract, so V1 is a new canonical boundary rather than a drop-in compatible shape. Directly switching a legacy consumer is breaking because legacy payload names, units, scope, timestamps, and acknowledgements are inconsistent or missing.

Mitigation:

1. Capture one legacy fixture per migrated behavior without credentials or personal data.
2. Write a named adapter from that fixture to V1.
3. Test the adapter and V1 schema together.
4. Switch one producer/consumer pair at a time.
5. Remove the adapter only after all relevant legacy producers are retired.
